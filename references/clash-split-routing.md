# 在现有 Clash 配置中合并分流

适用于支持 MRS 的 Mihomo 客户端，例如 Clash Verge Rev。用户要求“国内直连、海外代理”时，新部署在生成节点配置后执行；已有配置只做必要合并，不重建节点。任何能读取文件、编辑 YAML 并运行客户端校验的 Agent 都可执行，不依赖特定 Agent、路径或私有服务器。

模板是 [assets/clash-split-routing.yaml](../assets/clash-split-routing.yaml)，保留用户提供的 5 个 MetaCubeX MRS 规则集与 7 条规则原值。它是**合并片段，不是完整配置**，不能单独导入，也不能直接用于 Shadowrocket。

## 1. 找到真实生效的配置并备份

从用户本次提供的文件或已授权的客户端状态确认当前选中的配置。Clash Verge 导入后可能使用自己的副本，不能只修改原下载文件；也不要只改下次生成就会覆盖的运行时文件。核对当前配置、全局扩展、配置专用扩展以及“编辑规则”中的 `prepend`、`append`、`delete` 和脚本，找出规则最终从何处生成。

Clash Verge 的手动入口是“订阅 → 右键当前配置 → 编辑文件”；已有前置规则在同一卡片的“编辑规则 → prepend”中修改。若通过“扩展配置”写 `rules`，该列表会整体替换上一步的列表，应写入合并后的完整结果，不能把它当作追加操作。

在用户私有目录备份将要编辑的源文件及选择状态，记录恢复位置。目录 700，含凭据的文件 600；不把完整配置、节点链接或日志中的秘密写入本公开仓库。无需读取 VPS、轮换凭据或重新部署。

记录并保留节点与凭据、代理组成员及当前选择、各监听端口、DNS、TUN、IPv6、系统代理和其他无关设置。先比较最终有效规则，再选择改动最少、持久生效的来源；不要同时在基础文件和扩展中插入同一批规则。

## 2. 按实际配置合并

1. **确定策略名。** 片段引用的 `PROXY` 必须存在。若用户实际组名不同，把片段内所有规则策略及两个 anchor 的 `proxy` 同步替换为真实代理组名；展开 anchor 后则改 5 个 provider 的 `proxy`。不为了匹配名字重命名用户的组。保留组当前选项；如果它选中了 `DIRECT`，匹配该组的海外流量和规则集下载也会直连，需向用户说明。
2. **合并映射。** 顶层 `rule-anchor`、`rule-providers`、`rules` 各只有一个，不能把整段直接追加导致重复键。逐项比较同名 provider：内容相同则复用，内容不同则保留原项，为新增项使用唯一名称，并同步对应 `RULE-SET` 引用。缓存 `path` 也不能与其他 provider 冲突，应位于本次 Mihomo 工作目录允许的位置。
3. **处理 YAML。** 新增 `&ip`、`&domain` 若与原文件 anchor 重名，使用唯一名称并同步 `*` 引用，或把相应字段展开到每个 provider。使用支持当前 YAML merge key 的安全解析器，拒绝重复映射键；若工具不支持 `<<`，先展开再校验。不要用字符串整段替换、普通对象浅合并或重复键的“最后一个获胜”行为覆盖旧配置。尽量保留注释，仅对相关 schema 合并，其他自定义字段照原样保留。
4. **核对顺序。** 规则从上往下匹配。保留原有局域网、AI 站点、进程等特殊规则及其相对顺序；新增分流的前 6 条维持模板顺序，放在最终兜底之前。若旧规则与新分流重叠，明确哪条应优先，再形成最终顺序，不能默默改变原有特殊规则的意图。Clash Verge 的前置规则会排在基础 `rules` 之前；其有效结果也必须检查。
5. **只保留一个最终兜底。** 合并时去掉重复的终结 `MATCH`，让符合用户目标的最终 `MATCH,<实际代理组>` 位于有效规则末尾。原有 `MATCH` 后的规则不会生效，`append` 到它后面也无法实现预期分流。若原兜底策略不同且用途不清楚，先列出具体冲突，再解决这个必要问题。不要额外添加用户未要求的绕过或阻止规则。

模板中的 `interval: 86400` 表示每天更新，provider 的 `proxy` 指规则集下载所用策略，并非规则本身的流量目标。`cn_ip` 与 `GEOIP,CN` 覆盖范围可能重叠；本模板忠实保留两者，`GEOIP,CN` 另依赖客户端可用的 GeoIP 数据，不能只验证 5 个 MRS 就认为全部资源就绪。后续精简应单独说明依据，不擅自删除。

## 3. 校验、应用与回退

在私有候选文件中完成合并，使用当前应用实际内核进行配置校验。先根据该版本的 `--help` 确认参数，常见形式为：

```bash
"$MIHOMO_BIN" -t -d "$PRIVATE_TEST_DIR" -f "$PRIVATE_CANDIDATE"
```

测试目录中的相对 provider 路径与正式目录独立。检查 5 个 provider 可下载、格式正确、加载后规则数非零，并检查 GeoIP 数据可用；只收到 HTTP 成功响应不代表规则集已正确加载。下载失败时检查实际代理组与所选节点，不自动改成 `DIRECT` 或换来源。

独立试运行时另用空闲监听端口和控制端口，关闭测试实例的 TUN，不改系统代理；只终止自己启动的进程。测试方式可参考 [verify-and-diagnose.md](verify-and-diagnose.md)。先比较候选与原文件，确认改动仅涉及规则集、规则及必要的名称适配，再应用到已确认的持久源，刷新当前配置。

验收必须检查真实应用的有效规则、Rule 模式、所选节点和 provider 状态，并发起请求观察“连接”中的命中规则与最终链：已知国内域名应按预期 `DIRECT`，已知海外域名应通过实际代理组及节点，已有特殊规则仍命中预期策略。按本次实际入口测试，不能用隔离实例成功代替应用已生效；无法操作客户端时，明确保留这项待用户验证，不报告全部完成。

TUN 负责流量入口，规则负责进入内核后的去向；开 TUN 不等于全局代理。仅加入此片段不证明 DNS、IPv6 或所有应用都已被覆盖，不自动开关 TUN、系统代理或修改 DNS/IPv6。遇到相关问题先收集证据，另作针对性调整。

校验、下载或真实分流失败且本次修改已影响应用时，恢复备份的源文件和原配置选择并刷新，复查原连接恢复。记录脱敏差异、测试结果、未验证范围与回退位置。此流程是确定性配置合并，记录 `jev_called: false`，原因是无需重复语义分类；不让模型评分代替真实验收。
